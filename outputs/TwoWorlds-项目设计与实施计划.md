## 1. 产品要做成什么

TwoWorlds 是面向异地情侣的双人 AI 互动剧本平台。

两个人进入同一个故事，却身处不同位置、掌握不同信息。你看到的线索，可能正是对方操作机关所缺少的部分。双方通过交流、推理与配合推进剧情；AI 扮演 NPC、补充场景叙述，让每次体验有变化，游戏的正确答案、权限、因果关系和通关条件始终由程序判定。

核心体验是“我们一起完成了一段只有两个人才能完成的故事”。首版先验证这一体验，暂不扩展到多人社交、开放世界或无限生成剧本。

### 产品原则

1. **两个人都不可替代。** 关键流程同时需要双方信息与操作，避免一人代打、一人旁观。
2. **换设备也能继续。** 手机和电脑访问同一个账号、同一个云端存档。
3. **每个剧本独立保存。** 切换剧本不会覆盖另一段旅程。
4. **AI 负责表达，程序负责事实。** NPC 不能擅自发放道具、解锁章节或宣布通关。
5. **异常也能说清楚。** 用户能看到正在同步、连接中断、操作冲突或需要重试，而不是不知情地丢失进度。

## 2. 支持的平台与首版范围

### 平台

采用 Vue 3 + TypeScript + PWA，一套前端适配：

| 设备 | 首版使用方式 | 验证要求 |
| --- | --- | --- |
| iPhone | Safari 打开网址，可添加到主屏幕 | 实机检查安装入口、键盘、切后台后的恢复 |
| Android | 浏览器打开，可在支持的环境安装 PWA | 实机检查安装、横竖屏、断网重连 |
| 电脑 | 浏览器打开，支持的浏览器可安装 | 双窗口、双账号、刷新恢复与键盘操作 |

PWA 首版不包含 App Store、安卓应用商店上架。离线时可显示已缓存的界面外壳，但不能操作机关、调用 AI 或提交存档；这类行为需要服务器确认。

### 首版必须包含

- 创建个人身份，生成个人恢复密钥；另一台设备可用密钥恢复原身份。
- 创建双人房间，邀请另一人加入，固定 A/B 两个角色。
- 两个可选择、可完整通关的原创短剧本。
- 每个房间、每个剧本一个独立存档。
- 双方不同线索、不同操作权限、明确的合作前置条件。
- 剧情阅读、线索查看与分享、机关输入、NPC 文字对话。
- 服务端保存进度；刷新、重启、换设备后恢复。
- 双人实时同步，断线后恢复最新状态。
- 并发冲突处理、请求去重、越权访问保护。
- 本地运行说明、MongoDB 部署配置、测试与部署检查清单。

### 后续扩展

| 能力 | 本次处理 | 后续真正实现的内容 |
| --- | --- | --- |
| 双人实时语音 | 预留接口与能力状态 | LiveKit/WebRTC、短期房间凭证、麦克风控制、弱网重连 |
| AI NPC 语音 | 预留 ASR/TTS 适配层 | 语音输入、转写、合成、打断播放、字幕同步 |
| 邮箱/第三方登录 | 留出身份迁移边界 | 登录、找回、会话撤销、绑定既有匿名存档 |
| 更多剧本 | 先做可扩展剧本结构 | 作者工具、内容审核、版本发布与兼容 |
| 多个存档槽/重复开局 | 首版每剧本一个存档 | 新建局次、完成档归档、多个结局、历史回看 |
| 商业化 | 不进入核心开发 | 购买剧本、会员、支付、订单与退款 |

## 3. 一次完整的用户旅程

### 环节一：进入平台

用户首次打开平台，输入显示名称，创建个人身份。服务器生成身份标识与高强度恢复密钥，并提示用户保存。

恢复密钥用于在新设备登录，不能把用户 ID、昵称或房间号当作登录凭证。界面清楚说明：首版没有邮箱找回，遗失恢复密钥且丢失现有会话后，无法证明自己是存档拥有者。

验收：用户甲在电脑创建身份后，可在另一浏览器恢复同一身份；用户乙知道甲的 ID 也不能登录甲的账号。

### 环节二：建立双人房间

甲创建房间，占据 A 位；系统提供邀请链接或邀请凭证。乙用自己的身份加入，占据 B 位。链接只用于加入房间，不授予甲的个人身份。

房间只容纳两人。加入操作必须在数据库中原子完成；两个人同时竞争 B 位时，只能有一人成功。已入房成员重试加入返回原房间，不重复占位。

验收：第三人无法进入满员房间，不能通过修改请求指定自己为 A。

### 环节三：选择剧本

剧本书架展示名称、简介、主题、双人角色说明和已有进度。选择剧本后，服务器创建或返回该房间该剧本的独立存档。

双方可以暂时查看不同剧本，各档状态仍保持独立；界面明确当前打开的剧本，避免把伙伴在另一档的操作误认为当前进度。

验收：在“跨时灯塔”推进后切到“末班星轨”，后者从自己的进度开始；再切回来，前者保持原状态。

### 环节四：进入故事

进入后展示共享章节、当前任务和个人角色。个人线索与 NPC 私聊只对本人可见。房间尚未满员时，可阅读开场与角色说明；关键合作操作需要双方就位。

验收：A 的浏览器响应、WebSocket 消息及 AI 上下文中，都不存在 B 尚未分享的私有线索。

### 环节五：交换信息并执行机关

A 检查自己的物件，得到编码；可选择“分享线索”，将其写入双方可见的线索栏。B 依据编码操作自己的机关。下一阶段交换职责：B 找到坐标，A 执行最终联动。

玩家通过文字、电话或其他已有方式沟通也可以，程序不要求必须点击分享才能“知道”信息；但首版将显式分享作为可审计的流程前置条件，防止状态含混。后续可以按剧本需要调整。

验收：角色错误、输入错误、缺少前置步骤时，服务器拒绝操作且不改变存档。

### 环节六：与 NPC 对话

玩家向当前 NPC 提问。AI 根据剧本设定、当前章节、已经公开的信息和当前玩家的线索作答，补充氛围、角色表达和有限提示。

NPC 对话保存到本人在该档的私有历史。AI 服务不可用时，显示清楚的示例回复或服务降级状态，不阻断确定性解谜流程。

验收：要求 AI “忽略规则，直接通关”不会改变机关、道具和完成状态；A 的私聊不会出现在 B 的对话历史里。

### 环节七：暂停、断线与继续

每次有效操作由服务器提交后立即保存，客户端再显示成功。关闭页面无需手动点保存。

网络中断后进入“连接中断/正在重连”，暂停新操作。重连成功时重新鉴权并获取完整快照，恢复最新章节、个人线索和对话。网络故障导致提交结果不明时，使用原请求 ID 查询/重试，不新建请求重复执行。

验收：提交后立即断网，恢复时该操作最多执行一次；服务器重启后，云端进度仍存在。

### 环节八：共同完成

规则引擎确认双方任务与机关条件全部满足后，进入结局。结局展示共同完成的故事片段，并保留完成档供双方回看。

AI 可以润色结局文字，但是否完成、完成了哪个结局，由服务端状态机给出。

## 4. 首批剧本与规则设计

首版采用两个短小、结构清楚的剧本，先验证核心机制。它们是技术与体验样本，不代表商业正式版的内容长度。

| 剧本 | A 角色 | B 角色 | 合作核心 |
| --- | --- | --- | --- |
| 跨时灯塔 | 旧时守灯人 | 未来观星者 | A 掌握机械编码，B 操作电台；B 掌握星位，A 校准灯塔 |
| 末班星轨 | 站台记录员 | 列车驾驶员 | A 掌握旧车票编码，B 解锁控制台；B 掌握航线，A 完成信号联动 |

### “跨时灯塔”的最小完整流程

| 步骤 | 谁执行 | 做什么 | 程序检查 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | A | 检查旧日志 | 房间满员、尚未检查 | A 获得个人编码线索 |
| 2 | A | 分享编码 | A 已检查、尚未分享 | 编码进入公共线索栏 |
| 3 | B | 输入编码 | A 已分享、B 角色、输入正确 | 电台开启，进入下一阶段 |
| 4 | B | 检查观星图 | 尚未检查 | B 获得个人星位线索 |
| 5 | B | 分享星位 | 电台已开启、B 已检查 | 星位进入公共线索栏 |
| 6 | A | 校准灯塔 | B 已分享、A 角色、星位正确 | 双方完成剧本 |

允许不破坏因果的提前观察，例如 B 可以先查看星图，但分享与最终机关仍受阶段限制。机关选择、正确答案和状态迁移都存在服务器剧本定义中，不能把完整答案表发送到浏览器。

### 规则引擎的形式

输入：当前完整状态、服务器确认的玩家角色、已验证的命令。  
输出：新状态、需要展示的事件，或明确的业务错误。  
要求：无网络调用、无模型调用、无数据库写入，相同输入必然得到相同输出。

状态示例：

```text
开场 stage=0
  └─ A 观察 → A 分享 → B 正确输入
       └─ 联动 stage=1
            └─ B 观察 → B 分享 → A 正确校准
                 └─ 完成 stage=2
```

“状态机”表示章节与机关状态，不代表 NPC 可以自由改变的叙事文本。AI 生成的场景补充作为文字附加到确定的章节事实之上。

## 5. 总体技术架构

```text
iPhone / Android / 电脑
          │
   Vue 3 + TypeScript + PWA
          │ HTTPS：查询、提交、恢复身份
          │ WSS：鉴权后推送个人可见快照
          ▼
       FastAPI
          │
          ├─ 身份与房间服务：谁是谁、属于哪个房间
          ├─ 存档应用服务：鉴权、幂等、版本、流程编排
          ├─ 确定性规则引擎：角色权限、前置条件、因果和通关
          ├─ 可见性投影：公共内容 + 当前玩家私有内容
          ├─ LangGraph：剧情补充、NPC 对话、文本检查
          └─ 语音适配接口：首版 disabled
                    │
             Repository 持久化接口
                    │
                 MongoDB
       身份 / 会话 / 房间 / 独立剧本存档
```

### 为什么这样拆

| 模块 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 前端 | 展示、输入、连接状态、版本恢复 | 不裁决通关，不保存完整谜底 |
| API | 校验请求格式、认证、返回响应 | 不在路由中堆叠游戏逻辑 |
| 应用服务 | 读取、授权、调用引擎、提交与冲突处理 | 不让 AI 直接写状态 |
| 规则引擎 | 确定性检查与状态迁移 | 不联网、不调用数据库或模型 |
| 可见性投影 | 按身份裁剪可返回内容 | 不信任前端隐藏元素作为权限保障 |
| AI 工作流 | 根据可见事实生成受限文本 | 不拥有解锁、发道具、修改答案的工具 |
| 仓储 | 索引、持久化、原子提交 | 不决定玩家能做哪个机关动作 |

已检查 README、后端依赖、API、身份会话、LangGraph 图和对话生成实现。

- 保留思路：前后端分离、Python 分层、FastAPI、WebSocket 首帧认证、LangGraph 编排、Mongo 持久化、图实例复用。
- 更换界面：原有 Phaser/JavaScript UI 改为适合手机和桌面的 Vue PWA。
- 重建身份边界：原会话入口接受客户端 player_id，不能直接作为本产品的存档所有权认证。
- 扩充业务：新增双人房间、剧本版本、独立存档、角色权限、确定性规则、投影、幂等和 CAS。
- 暂缓复杂 RAG：首版剧本事实来自服务端审核定义，不抓取外部资料；后续确有需求时再做检索与内容治理。

## 6. 数据设计与隔离

### 主要实体

| 实体 | 关键字段 | 约束 |
| --- | --- | --- |
| Account 个人身份 | id、name、recovery_digest、created_at | 恢复密钥摘要唯一，明文只在创建时展示 |
| Session 登录会话 | token_digest、account_id、expires_at | 凭证摘要唯一，显式验证过期时间 |
| Pair 双人房间 | id、member_a、member_b、invite_digest、invite_expires_at、version | B 为空时才可原子加入；邀请过期或满员后失效 |
| Save 剧本存档 | id、pair_id、script_id、script_version、version、state、dialogues、receipts、updated_at | 首版 pair_id + script_id 唯一 |
| Script 剧本定义 | id、content_version、public_metadata、private_facts、rules | 发布后版本不可原地修改，旧档绑定旧版本 |

### 一份存档保存什么

```text
Save
├─ 所属房间与剧本版本
├─ 版本号 version
├─ 完整规则状态（服务端专用）
│  ├─ 章节与机关状态
│  ├─ A/B 各自检查、分享、持有信息
│  └─ 完成标志与结局编号
├─ 公共剧情事件（保留最近 30 条）
├─ A 的私有 NPC 对话（保留最近 20 轮）
├─ B 的私有 NPC 对话（保留最近 20 轮）
└─ 幂等回执（首版最多 512 个，不静默删除）
```

512 次为首版单档接受命令的明确上限，不是正式商业版的目标。两个短剧本足够使用；达到上限显式提示，后续用事务化独立回执与归档设计解除限制，不能通过删除旧回执破坏重试安全。

### 三层隔离

1. **房间隔离：** 每次访问先用服务器身份检查成员关系；知道存档 ID 不代表有权访问。无权访问统一返回 404，减少资源存在性泄露。
2. **剧本隔离：** 不同 script_id 对应不同存档、版本、对话和回执。
3. **角色隔离：** 同一档内，A 只能收到公共信息和 A 私有内容，B 同理。所有 HTTP 与 WS 复用同一投影逻辑。

AI 上下文也只能读取该投影，而不是先读取完整存档再依赖提示词要求“不泄露”。这样能减少实际数据暴露，但不能保证模型不会猜测或编造信息，因此 NPC 文字不能成为新的权威谜题事实。

## 7. 双人同步、并发与断线恢复

### 正常提交

```text
用户点击机关操作
 → 前端生成 request_id，并携带当前 expected_version
 → 后端确认身份、成员、角色
 → 查询是否已有同一请求回执
 → 检查版本与规则条件
 → 单文档原子提交：新状态 + 新版本 + 回执
 → 返回本人的可见快照
 → 另一个客户端通过 WSS 收到自己的可见快照
```

### 请求结构

```json
{
  "request_id": "由客户端生成的 UUID",
  "expected_version": 12,
  "kind": "unlock",
  "value": "玩家输入"
}
```

客户端不能提交自己的 role、account_id、完成标志或完整状态来覆盖服务器。

### 关键情况如何处理

| 情况 | 服务端行为 | 用户看到什么 |
| --- | --- | --- |
| 两人基于同一版本提交 | 数据库 CAS 只允许一个成功，另一个 409 | 刷新到新进度，保留输入，提示重新确认 |
| 同一请求因网络重发 | 按 actor + request_id 返回已处理确认，不重复执行 | 恢复确认，无重复推进 |
| 同一 ID 被换内容重用 | 校验请求指纹，返回 409 | 明确提示请求冲突 |
| 请求已成功但响应丢失 | 重试原 ID，先识别回执再检查旧版本 | 能确认上次已成功 |
| WebSocket 断开 | 浏览器退避重连，重新鉴权、获取完整快照 | 显示重连，暂禁操作 |
| 手机切后台 | 回到前台重新连接并拉取最新快照 | 最新进度覆盖旧画面 |
| 两个设备使用同一账号 | 都能读取；提交仍走版本检查 | 不发生后写覆盖先写 |
| 服务器进程重启 | 从 Mongo 恢复，客户端重新连接 | 进度保留 |
| 数据库不可用 | 返回错误，不伪造成功、不降级写内存 | 提示稍后重试，保留未确认请求 |

### 首版实时策略

使用鉴权后的 WebSocket 发送完整的“个人可见快照”。首版服务端每约 250ms 检查相关存档版本，版本变化即推送；每约 10 秒发送心跳快照。

这种方式省去首版的消息队列和事件补偿，多个进程也能通过同一数据库发现变化，但轮询会增加数据库负载。完成负载测试后，再决定迁移至 Mongo Change Streams 或 Redis 广播；迁移时保留客户端版本检查与全量恢复机制。

前端仅接受不低于当前版本的快照，防止迟到的 HTTP 响应覆盖较新的 WS 状态。切换剧本时取消旧连接与未完成读取，防止旧档响应串到新档。

Mongo 单文档原子性及预期值过滤依据：[MongoDB 官方说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)。

## 8. AI 设计与语音扩展

### LangGraph 工作流

```text
授权后的个人快照
 → 整理场景、角色、已知事实与最近本人对话
 → 按任务生成场景补充或 NPC 回复
 → 检查文本类型、长度、空内容与输出格式
 → 应用服务复查版本并保存文本
```

图不持有修改游戏状态的工具。权威存档由应用服务统一提交，避免模型记忆与游戏状态分别写入后发生不一致。

### 可以交给 AI 的内容

- 当前确定章节的环境描写、情绪变化和转场润色。
- 有角色设定的 NPC 问答。
- 基于已知事实的有限提示。
- 确定结局之上的文字润色。

### 必须由程序决定的内容

- 什么人能操作、哪个道具真实存在、机关能否开启。
- 正确答案、操作前置条件、章节迁移、结局判定。
- 哪条线索已经公开、哪段信息属于哪一位玩家。

### 模型接入与失败处理

首版默认无付费调用的示例模式，方便没有密钥也能测试整体流程。真实模型通过可替换 Provider 接入，可使用参考仓库已有的 DashScope/Qwen 方向，具体模型由部署配置指定。

密钥只存后端环境变量，不进入前端、浏览器缓存或日志。设置超时、输出长度和调用并发上限；错误时明确区分示例、真实 AI 与降级回复。测试使用模拟服务验证请求，不擅自发起付费调用。

AI 生成在数据库原子提交之前进行，期间不持有数据库锁。生成后版本已变化时，拒绝陈旧提交并提示重试；不自动反复调用模型消耗费用。

### 语音接口预留

| 接口 | 首版约定 | 未来实现 |
| --- | --- | --- |
| VoiceRoomProvider | 返回未启用能力 | 为当前房间签发短期 LiveKit 凭证 |
| SpeechProvider.transcribe | 定义输入、输出、超时和错误形式 | ASR 语音转文本 |
| SpeechProvider.synthesize | 定义文本、声音和音频流形式 | TTS 生成 NPC 语音 |
| capability API | 鉴权后返回 enabled=false | 前端按已配置能力显示入口 |

语音实现后仍必须检查成员、限定房间、避免跨房监听；录音与保存需有清楚的用户控制。首版不申请麦克风权限，也不显示能用但实际无功能的通话按钮。

| 页面/区域 | 实现内容 | 关键状态 |
| --- | --- | --- |

| 共享故事区 | 当前章节、公共事件、任务 | 等待另一人步骤、已推进 |

所有操作支持键盘与触控，重要按钮在手机上容易点按；遵循减少动态效果偏好。用户界面不显示数据库、CAS、LangGraph 等实现术语，用“进度已更新，请确认后再试”等语言表达。

## 11. 分阶段开发计划

采用可验收的小步交付。每阶段先定义行为与失败测试，再实现并验证，不一次性铺开全部功能。

### 阶段 0：基线与设计确认

**做什么：** 审查参考仓库、确定首版边界、定义角色与状态流、建立工程目录和配置样例。

**交付：** 本设计稿、仓库审查说明、任务清单、待验证事项。

**验收：** 用户确认首版方向；开发者能明确说明哪些功能在本次完成，哪些只留接口。

**当前进展：** 参考仓库审查与设计初稿已完成；尚待审阅。首批后端测试已起草，但缺少实现，不能视为通过。

### 阶段 1：确定性规则与独立存档

**做什么：**

1. 定义两套剧本数据与不可变版本。
2. 编写纯 Python 状态机与角色可见性投影。
3. 实现 Mongo 仓储、唯一索引、版本 CAS、幂等回执。
4. 提供 SQLite 文件演示适配器，复用相同契约。

**交付：** 无 UI 也能由测试完整通关的规则与存档核心。

**验收：** 错误角色/答案/顺序不改变状态；两剧本互不覆盖；文件/数据库重开后可恢复；同版本并发只有一个提交成功。

### 阶段 2：身份、配对与后端 API

**做什么：**

1. 创建身份、摘要存储、恢复密钥换取会话、显式校验会话过期。
2. 创建邀请、有效期、原子加入、双人上限。
3. 接通剧本、存档、命令和错误响应 API。
4. 每条入口统一执行认证与成员校验，增加输入限制。

**交付：** 可用 HTTP 请求完成“两个身份 → 房间 → 独立剧本 → 通关”。

**验收：** 不凭用户 ID 认领身份；第三人无法读取/提交；并发抢位只有一人成功；新设备恢复身份后看到原存档。

### 阶段 3：Vue PWA 与完整双人体验

**做什么：**

1. 身份创建与恢复、房间邀请、剧本书架。
2. 故事阅读、个人线索、分享、机关输入与结局。
3. 接入 WS、心跳、退避重连、前台恢复与读取补偿。
4. 幂等重试、版本防回退、切档取消旧请求。
5. 配置 PWA 与移动布局；API/认证数据不进入离线缓存。

**交付：** 两台设备可以一起玩、暂停和继续的文字互动版本。

**验收：** 两个独立浏览器身份可通关；刷新、断网、切档与手机宽度布局正常；伙伴私有信息不进入本机网络响应。

### 阶段 4：AI 对话、剧情润色与语音边界

**做什么：**

1. 构建 LangGraph 文本工作流与可替换模型 Provider。
2. 接通本人 NPC 历史，生成内容与规则状态分离。
3. 配置超时、输出限制、并发限制与示例降级。
4. 定义 VoiceRoomProvider、SpeechProvider 与 capability API。

**交付：** 没有模型密钥也能运行，有密钥时能接通真实模型的版本；语音明确显示未启用。

**验收：** AI 不越过规则引擎；其输入不含对方隐藏信息；服务超时不破坏存档；外人无法读取语音房间能力。

### 阶段 5：测试、部署与交付

**做什么：**

1. 补齐安全、重连、并发、幂等与真 Mongo 契约测试。
2. 用双浏览器完成端到端验收，保存可追溯结果。
3. 提供 Dockerfile、Compose、反向代理、环境变量和 CI。
4. 验证数据库重启、备份恢复、健康检查、日志脱敏与 HTTPS。
5. 汇总已实现、实际通过、未验证和已知限制。

**交付：** 源码、运行手册、部署手册、测试报告和演示入口（仅在实际启动/部署成功后提供）。

**验收：** 按 README 在干净环境可启动；云部署显式使用 Mongo；不能用 SQLite 测试结果代替 Mongo、真机或生产验证。

### 后续迭代顺序

先做正式身份与会话管理、更多剧本与存档槽，再做双人实时语音；最后接入 NPC 的 ASR/TTS、作者工具与商业化。若语音是首批试用用户的关键需求，可在完成核心同步验证后提前，但不影响规则与存档模块边界。

## 12. 测试与验收矩阵

| 测试层 | 重点场景 | 通过条件 |
| --- | --- | --- |
| 规则单测 | 正确解谜、角色错误、错答案、跳步骤、完成后重复操作 | 只有合法动作改变状态 |
| 投影单测 | A/B 私有线索、本人对话、公开线索 | 私有数据不进入另一人投影 |

| 并发测试 | 同版本双提交、双人抢 B 位、同档重复创建 | 唯一胜者或返回同一资源 |
| 幂等测试 | 原 ID 原内容、原 ID 改内容、响应丢失再试 | 不重复推进、不接受变造重放 |
| 持久化测试 | 服务重启、数据库重新连接、两个剧本 | 进度保留且互不覆盖 |
| AI 测试 | 提示注入、超时、无效格式、并发版本变化 | 不改变规则，不带入隐藏上下文 |
| 浏览器测试 | 双账号通关、刷新、切档、断网重连 | 能继续且版本不倒退 |

重要补充：并发验证必须覆盖数据库原子提交本身，不能只用进程内锁证明安全。真实 Mongo 测试无法运行时应明确标记未验证，不能静默跳过后宣称全部通过。

## 13. 部署与运维设计

### 本地开发

- 前端开发服务器 + FastAPI + MongoDB 为完整开发路径。
- 没有 Mongo/Docker 时可显式选择 SQLite 文件演示，保证不依赖云服务也能检查交互。
- 真实 AI 默认为关闭；填写后端配置后单独验证。
- 本机已检测到 Python、Node、Docker 客户端，但 Docker daemon 尚未运行。

### 首版部署

```text
公网域名 + TLS
      ↓
反向代理：静态前端 /api / WebSocket Upgrade
      ↓
FastAPI 应用容器
      ↓
MongoDB 持久化卷或托管 Mongo
```

- 前后端同域，精确设置允许 Origin，不使用任意跨域授权。
- Mongo 不直接发布公网端口，启用身份验证与持久化。
- 生产环境必须指定 Mongo URI，缺少依赖则启动失败，不静默写入本地临时文件。
- 凭证、邀请、恢复密钥、NPC 私聊正文不写入普通访问日志。
- 健康检查区分进程存活与数据库就绪。
- 备份不仅要生成，还要在测试环境恢复并检查进度。
- 公网上线前设置边缘限频、AI 费用与并发限制；多实例共享限制需独立验证。
- 初期部署一个应用实例，之后根据 WS 数量、数据库读取量和模型延迟决定扩容。

部署平台和预算尚未指定，因此本文不虚构托管地址、费用或已部署状态。基础容器与环境变量约定先保持可迁移。

## 14. 关键风险与首版取舍

| 风险/取舍 | 首版处理 | 后续升级 |
| --- | --- | --- |
| 个人恢复密钥丢失或泄露 | 明确保存提示、摘要存储、限制恢复尝试 | 绑定邮箱/第三方身份、撤销与轮换 |
| AI 编造规则或线索 | 只输入可见事实；程序决定机关；文字标识清楚 | 剧本专属评估集、内容审查 |
| 并发操作覆盖 | Mongo CAS + 同文档状态与回执 | 根据负载扩展事件/事务方案 |
| WS 轮询增加数据库负载 | 小规模优先、记录指标 | Change Streams/消息广播 |
| 文档或回执无限增长 | 历史有界、512 次命令上限 | 归档与独立事务化回执 |
| 内容更新破坏老档 | 存档固定 script_version | 明确的迁移工具与兼容测试 |
| PWA 后台连接不稳定 | 前台重新连接、全量恢复 | 真机持续优化 |
| SQLite 演示与 Mongo 行为不同 | 共用契约测试，真库单独验收 | 在 CI 持续跑 Mongo |

## 15. 交给 Codex 的完成标准

首版只有同时满足下列条件，才可以称为“完成最小可运行版本”：

- 两个不同身份能进入同一房间，并完整通关两个剧本。
- 双方看到不同线索和操作，外人无权读写。
- 每剧本独立存档；刷新、重启与跨设备恢复保持进度。
- 网络重试不重复执行；同时提交不互相覆盖。
- AI 对话真实接入或清楚标示示例/降级，不影响确定性规则。
- iPhone、Android、电脑的适配已有明确验证记录；没有真机测试时明确写出。
- Vue 类型检查、前端构建、后端测试和实际执行的 E2E 测试通过。
- Docker/Mongo 配置与运行文档完整；未部署或未跑真库的部分如实记录。
- 提供具体交付文件与下一步，不把计划、测试草稿或静态演示称为完成产品。
