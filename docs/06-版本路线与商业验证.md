# 06 · 版本路线与商业验证

> v0.2 设计提案 · 2026-10-26。收入、价格、体验指标和用户数量均为试验假设，没有真实营收或市场验证结果。

## 1. 这个项目最终希望成为什么

长期目标是一个能持续上新原创内容的双人互动剧本平台：用户与搭档选择今晚的故事，在不同角色视角中探索，保存每个世界的进度，获得共同完成的故事回顾。

平台能力与故事内容分开成长。平台解决身份、关系、存档、同步和AI边界；内容解决人物、世界、谜题、因果与选择。增加一个剧本，不等于复制一个后端项目。

## 2. 产品路线分层

| 阶段 | 用户价值 | 范围 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| R0 设计基线 | 目标与工作清楚 | 本文档集、两剧本规则、开发与验收清单 | 审阅范围与取舍，形成可执行基线 |
| R1 可玩原型 | 两个人可以稳定玩完并看见世界变化 | 两短篇、场景插画/因果动效/基础音频、多端网页、独立存档、示例NPC、恢复与同步 | 核心测试、视听验收、双浏览器与真实试玩可完成 |
| R2 内容验证 | 愿意再约一次一起玩 | 改进两篇，增加第三种机制的短篇，补提示与回顾 | 新玩家不用开发者讲解也能推进，愿意再玩 |
| R3 关系与语音 | 在平台内更自然地沟通 | 会话管理增强、数据控制、LiveKit通话、静音与重连 | 跨端语音与隐私控制实测，成本与可靠性可接受 |
| R4 内容付费 | 为高质量故事持续买单 | 付费故事包、支付/订单/退款、客服与内容运营准备 | 真实付费测试通过，公开运营所需事项实际确认 |
| R5 连续故事与纪念册 | 长期共同回忆 | 长篇分章、受控记忆、多槽/重开、自愿分享纪念卡 | 版本、隐私、内容更新与长档回执方案已验证 |
| R6 AI语音与生态 | 更沉浸、更多内容 | NPC ASR/TTS、实时主持、受控作者工具、未来App | 有用户需求与费用依据，再单独设计和评估 |

R2 的第三剧本建议《雨夜旅馆》：双方询问不同NPC，利用经过审核的证词发现矛盾，验证信息推理能力。它是未来内容建议，不纳入当前两剧本验收。

## 3. 为什么首版先做两篇

早期聊天先提出一个七章故事，之后用户明确要求多剧本自由选择、独立存档。历史助手随后建议三个单章样本；当前迁入的正式稿收敛为两个短篇。

本次沿用两个短篇，理由是足以验证内容切换与隔离，同时控制内容制作量；但两篇必须是不同机制。若两个故事只换名字和密码，就没有证明通用平台成立。

七章连续故事、纪念册、三篇起步均可在审阅后调整，但需要同步资源和验收，不以旧助手建议自动扩张当前范围。

## 4. 首轮试玩安排

### 4.1 招募与流程

建议先约3对，再扩展至约10对情侣/双人搭档。由用户选择和联系参与者，开发助手不自行发送邀请、邮件或社交消息。

使用前说明：这是原型，可能有错误；不要求上传真实关系隐私；是否记录匿名操作与反馈由参与者选择；普通玩家通话不会默认交给AI。

每对完成：身份/邀请 → 第一篇 → 自愿选择是否玩第二篇 → 访谈 → 一周内自愿回访。观察者尽量不解释机关解法，只在阻断时记录帮助。

### 4.2 需要测什么

| 指标 | 如何记录 | 解释边界 |
| --- | --- | --- |
| 进入成功率 | 从打开链接到双方进入故事的对数 | 区分网络、邀请、登录与理解障碍 |
| 首次有效合作 | 第一条由对方动作产生且被利用的状态变化 | 不是两个人都打开页面就算合作 |
| 双方贡献 | 各自必要操作与讨论次数，匿名汇总 | 不通过偷偷录音分析 |
| 完成率与时长 | 完成结局的对数、耗时、提示次数 | 区分主动暂停和卡住退出 |
| 第二篇意愿 | 实际开始另一篇的人数 | 口头说喜欢与实际继续分开 |
| 再次约玩 | 一周内主动回来或主动约时间 | 搭档时间难对齐不全算产品失败 |
| 付费意愿 | 对明确的故事内容与价格询问 | 意向不等于付款 |
| 实际成本 | 每对每篇模型调用尝试、tokens、存储和服务成本 | 包含失败与放弃请求，不只成功写档 |

首轮只采必要事件：进入、加入、打开存档、命令接受/失败码、完成、请求提示、主动反馈。日志使用随机标识；不采密钥、私聊正文和用户未同意的关系信息。

## 5. 试验后怎么决定

以下是小样本决策参考，不是统计显著性结论：

| 观察 | 优先动作 |
| --- | --- |
| 多数人卡在登录或邀请 | 修入口与解释，再测玩法 |
| 一个人全程操作、另一人旁观 | 重做角色能力与必要贡献链 |
| 能通关但只是对答案 | 增加可试验因果与反馈，减少无意义操作 |
| 经常不知下一步能做什么 | 调整观察、目标、错误文案与三级提示 |
| 两篇都有人主动继续玩 | 扩充第三机制，测内容成本与复玩 |
| 喜欢但不愿付费 | 核对体验长度、内容价值、价格和替代方式 |
| 愿付费但模型成本太高 | 限定生成位置、缩短上下文、复用公开静态叙事 |
| 完成率低且改两轮仍无改善 | 暂停新增功能，重新判断目标用户和玩法 |

可将“10对中至少6对无开发者解题完成首篇，至少4对实际开始第二篇”作为初步观察目标。没有达到时先看原因，不机械判定失败；达到也不等于市场已验证。

## 6. 可能的收费方式

优先验证按故事包付费：保留免费体验篇，再给出有明确题材、时长和机制的双人故事包。早期可研究 ¥9.9–19.9/双人包，具体价格由内容质量、成本与真实测试决定。

首版不实现支付。未来做价格测试时，先交代真实可交付内容、试用限制和退款方式；不把“点击购买意向”当营收，也不通过没有内容的收费页面制造虚假成交。

| 收费方向 | 适用条件 | 当前处理 |
| --- | --- | --- |
| 双人故事包 | 用户愿为下一篇独立内容付费 | 首选后续试验 |
| 分章长篇 | 已证明连续故事的回访与制作能力 | R5再设计 |
| 订阅 | 有稳定上新与持续使用 | 现阶段无依据，不承诺 |
| NPC配音/特殊声音 | 增强体验且成本可计量 | 语音阶段验证 |
| 作者内容分成 | 作者工具、审核、版权、结算成熟 | 远期 |

盈利需要同时考虑故事制作、插画、模型、服务器、支付、客服、维护与获客，不能只算token。国内竞争较少、没有同类或未来一定盈利均未在本次工作中验证。

## 7. 风险与需要做的工作

| 风险 | 当前应对 | 进入公开运营前的工作 |
| --- | --- | --- |
| 玩法短浅 | 两机制与真实试玩 | 以重复使用和内容反馈迭代 |
| 内容耗时 | 短篇、通用原语、白名单内容 | 建立创作/审阅/发布流程与成本记录 |
| AI编造或不当输出 | 投影上下文、规则权威、示例降级 | 内容评估、投诉与处理流程 |
| 账号盗用/密码泄露 | Argon2id 哈希、HttpOnly Cookie 会话、登录与验证码限频 | 双因素、设备管理、异常登录提醒 |
| 隐私与共用记录 | 私聊分离、公共回顾、普通日志脱敏 | 明确双方共享数据删除与关系退出政策 |
| 监管与产品归类 | 先做受控原型，保留待确认事项 | 针对实际发行方式、生成内容、支付与数据另行确认要求 |
| 语音成本/后台不稳定 | 首版不宣称语音可用 | 真机弱网、权限、前后台与成本测量 |
| 运维故障 | 持久化、健康、恢复演练 | 监控、备份、响应流程与公共服务承诺 |

本文件不对法律资质或公开发行条件作已满足结论。正式公开运营时按当时实际方案获取适用的专业核对；技术原型通过不自动意味着商业发行准备完成。

## 9. 明确的设计决定

| ID | 决定 | 原因与后果 |
| --- | --- | --- |
| D-01 | 多剧本，首版两个短篇 | 满足切换与独立存档；控制制作范围 |
| D-02 | 单房间两席位，每剧本一个档 | 减少关系与局次复杂度；多槽后续做 |
| D-03 | 规则事实归程序，AI归表达 | 可解、可测、模型故障不阻断 |
| D-04 | Save单文档状态与回执原子写入 | 提供并发与网络重试的一致性基础 |
| D-05 | actor+request_id幂等、返回最新快照 | 旧响应重试仍确认，不回退画面 |
| D-06 | 同账号多设备允许，版本冲突确认 | 暂缓控制端租约；错误不静默重放 |
| D-07 | NPC私有文本，公开场景由模板保证 | 不把个人上下文生成的文字推送给伙伴 |
| D-08 | 线索分享默认可选 | 支持外部沟通；避免人为点击代替真实合作 |
| D-09 | 两种存储契约，生产只用Mongo | 方便本地演示，真库单独验收 |
| D-10 | 不默认录音，不共享私聊 | 减少无关隐私采集，明确语音边界 |

## 10. 审阅重点

这次最值得审阅的是：两套玩法是否符合“真正需要合作”、两短篇是否适合作为首版、当前的匿名身份/每剧本单档是否能接受，以及场景插画/因果动效/基础音频的首版范围。实时通话和任意NPC回复在线配音仍按后续路线推进。

没有明确答案的预算、云平台、具体模型、上线日期与真实手机条件不虚构。本版先提供可迁移配置与明确的验收工作，在对应阶段取得实际信息后更新。
