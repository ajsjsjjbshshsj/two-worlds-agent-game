## 2. 共用命令、证据和恢复规则

### 2.1 请求、响应和失败语义

- 写操作继续使用 `POST /api/saves/{save_id}/commands` 的 `request_id`、`expected_version`、`kind`、`args`。参数表给出 `args` 的完整形状，所有字段必填（含明确允许的 `null`），禁止多余字段、类型强转以及客户端提供角色、配置代次、样本值或判定结论。表里的「A」或「B」是唯一允许写入的角色。双方可读取各自快照、主动查询自己的回执；读取无版本变化。
- 操作表中 **+1** 表示存档版本及规则状态版本共同递增一次，产生一条已接受回执。多项证据写入、联动失效、里程碑、场景变化和回执可在同一次提交完成。**所有失败均不修改状态、版本、回执、事件或播放资格**，此前的提交保留。每行给出的失败码之外均适用下表的公共失败条件。
- 成功响应沿用已接受回执和当前角色投影。表中输出的 ID、许可或观测只出现在获授权的快照槽位。原始规则事件、内部证据账本和私有文本不进入响应。新的公开里程碑只在成功提交后发布，绑定唯一接受版本。
- 对合法命令信封，依次鉴权和确定成员角色 → 查已接受回执及指纹 → 检查 `expected_version`、容量和满员 → 领域校验。对扩展版领域命令依次检查已完成存档、动作角色、参数、重复完成的谜题里程碑及场景，再按操作表查当前引用和条件。遗留动作继续保留原语义；表列的扩展版拒绝码适用于新增门槛。固定错误正文不回显提交内容、证据是否存在于其他档或对端私有值。

| 公共条件 | 结果 | 恢复 |
| --- | --- | --- |
| 未认证／非成员或档不存在 | 现有 401／统一 404 | 验证会话或回到有权读取的存档 |
| 命令信封非法／动作参数非法 | HTTP 信封 `INVALID_INPUT`，领域入口 `INVALID_COMMAND`，操作参数 `INVALID_ARGUMENTS`，422 | 修正字段，在确认失败后新建命令 |
| 当前角色无权执行 | `ROLE_FORBIDDEN`，422 | 有权角色在自己的端执行，不能传入角色覆盖 |
| 已完档／谜题永久完成／场景不符或上游缺失 | `SAVE_COMPLETED`／拟议 `PUZZLE_COMPLETE`／`PRECONDITION_NOT_MET`，422 | 读取回顾、继续下一章或完成上游 |
| 合法输入不改变已有状态 | `NO_STATE_CHANGE`，422 | 沿用当前状态或已接受回执；同值不增加代次 |
| 引用未知、跨档、错类型、错归属、被替换或失效 | 拟议 `EVIDENCE_STALE`，422，统一响应 | 读取当前授权状态，按该章重新建立必要证明 |
| 当前物理/设备条件不足 | `PRECONDITION_NOT_MET`，或保留表内既有专用码，422 | 恢复实际条件，重取已失效的证明 |
| 请求版本已旧，或不同请求输掉 CAS | `VERSION_CONFLICT`，409 | 读取新版本后由玩家确认新命令，服务端不重放 |
| 已接受 UUID 换指纹／达到存档容量 | `REQUEST_ID_REUSED`／`SAVE_COMMAND_LIMIT`，409 | 网络重试保留原信封；满额仍可读取及查旧回执 |
| 房间尚未满员 | `PAIR_NOT_READY`，422 | 待搭档加入再提交 |

以上状态及详情采用现有错误信封。各章专用错误拟沿用领域错误的 422；本轮未修改映射。全局前置拒绝可先于领域拒绝，例如旧版本的错角色请求先得到 `VERSION_CONFLICT`；对使用当前版本的未完成档才断言 `ROLE_FORBIDDEN`。

### 2.2 ID、配置代次和同一次提交

- 每个挑战、观察、证据、批次、验证、锁和许可都有服务端生成的类型化 ID。推荐使用基于可信 Save ID、固定剧本版本、对象类型和将接受的存档版本派生的 UUID。单次操作若生成多个对象，各用不同类型或固定序号。派生可在纯规则中确定性复现，Save ID 由应用层提供。ID 可被引用，本身无权限；服务端只能在当前 Save 内匹配存储记录，并查类型、创建角色、父 ID、内容版本、活动槽及依赖版本。两端从快照取得被授权使用的引用。
- `expected_version` 是 CAS 门槛；`optics_rev`、`tide_config_rev`、`survey_rev`、`track_rev` 和 `drive_power_rev` 则是各谜题当前依赖的单调整数。初值为 0，相关配置实际改变时在同一次写入递增；多个字段在一个命令中改变只加一次。拒绝、回执复用、读操作和无关动作不推进该代次。即使物理值 A→B→A 再相等，当前代次仍比旧的高。
- 所有验证基于一次读取的存档聚合。规则引擎只产生候选状态。SQLite 用事务内带原版本谓词更新；MongoDB 用单文档带版本谓词替换。只有保存成功才认可候选状态、回执、公共历史和事件；输掉 CAS 后只重读检查同一请求的回执。此设计要求证据、设备与里程碑均在同一个版本化 Save 内，不能另写一个会领先于 Save 版本的证明表。
- 完整幂等键是 `save_id + actor_id + request_id`。已接受的同指纹（原 `expected_version`、动作和参数）返回原 `accepted_version`、`duplicate=true`、当前本人投影，不再次创建对象、递增配置代次或发布演出。同键已接受后换指纹一律拒绝。失败不留接受回执，网络不确定时原样查询/重试。玩家依据最新状态明确发起新尝试才使用新 UUID。
- 每种临时对象保留当前槽及至多一个被替换／失效的历史摘要，绑定其原创建版本及失效类别。读接口只按权限返回摘要，未知或已经被清理的旧引用仍走 `EVIDENCE_STALE`。永久里程碑及其接受版本独立保存，不从缓冲的事件反推。旧 UUID 的已接受回执继续保留。后续实现必须确认现有 512 条接受命令上限在最慢合法通关路径中仍有足够余量。

### 2.3 断线、投影与演出

| 类别 | 恢复规则 | 可见性 |
| --- | --- | --- |
| 已提交的动作 | 已提交的存档和本人回执为准；回执版本早于快照版本时，当前状态由快照决定 | 只回本人 `request_id` 与接受版本 |
| 未知是否提交／本地未提交 | 查原回执；`accepted=false` 仅表示当前未查到。需要继续重试时保留原信封。未发送的本地草稿不构成证据 | WS 与 HTTP 只从已提交状态投影，不传草稿 |
| 当前有效／历史失效证据 | 以当前绑定关系和代次判断，历史摘要只供说明，不列为可提交候选。退出、时间经过、服务重启本身不增加代次 | 分角色白名单。必要时只给另一端「已提交」「待补测」「锁已合」等授权结果 |
| 永久里程碑 | 完成事实持久，重连恢复正确章节和静帧；同 UUID 重试也不重复触发 | 双方可读获准事实与回顾。GET、首次/补偿 WS 快照及去重响应不携带一次性动作演出；后续送达重复或乱序快照不得播放第二遍 |

沿用当前 HTTP、命令响应、WS 和 NPC 输入的角色边界。公共回顾、错误、日志和 NPC 上下文不能间接携带另一端原始线索、活跃证明字段或完整状态；媒体也按角色授权。活跃证据与永久里程碑另建明确投影，客户端根据当前已接受版本与活动槽判断按钮可用性，服务器仍复验全部条件。

## 3. L03 · 信号锁定与错误回信恢复

**进入条件。** 在 `calibration` 已完成 L02 的持久对照里程碑 `beam_contrast_confirmed`，两边已发现原规则线索，初始状态 `IDLE`。开始挑战及锁定时都检查当前 90°／脉冲／琥珀；设置失准后仍可调整设备，回到此章继续。已达 L03 的章进度保持。

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| `IDLE` | 首次进入，尚未发行挑战 | B 发行 → `OPEN` |
| `OPEN` | B 发出新的 `challenge_id`，绑定 `optics_rev` 和本轮两拍 | A 正确回应 → `RESPONDED`；改光路 → `INVALIDATED`；B 主动换轮 → 新 `OPEN` |
| `RESPONDED` | 当前挑战已存 A 的真实回复，序列符合逆序规则 | B 验证 → `VERIFIED`；改光路失效或 B 主动换轮 |
| `VERIFIED` | B 以当前挑战引用核对服务器保存的回复 | B 锁定 → `LOCKED`；改光路失效或 B 主动换轮 |
| `INVALIDATED` | 有过挑战且相关配置改变，旧挑战退出当前槽 | 光路恢复后 B 发行新挑战 → `OPEN` |
| `LOCKED` | 消费当前已验证挑战并写 `signal_locked`，进入 `repair` | 本谜题终态；进入 L04 |

B 发起的挑战由服务端按每次实际发行的轮号在内容批准的至少两种不同形状序列间确定性轮换（验收例为短长、长短）。两个符号不同；A 的逆序说明只在自己卡上。错误的合法序列直接拒绝，**同一挑战仍在 `OPEN`**。A 修正时提交新 `request_id`，沿用 `challenge_id`。只有 B 换轮或光学失效重启才生成新的 `challenge_id`；旧轮即使回复形状碰巧正确也无效。

| 命令及完整参数 | 角色 | 原状态及前置 | 成功和授权输出 | 特定失败及恢复 | 版本 |
| --- | --- | --- | --- | --- | --- |
| `set_emitter({angle, pattern})` | A | 原校准场景及本人维护册前置；原角度与光型枚举 | 应用新值，增加 `optics_rev`，如有活挑战则失效；本人见装置，另一端见获准光学变化 | 原参数错误／`NO_STATE_CHANGE`；改回正确值后重新发起 | +1 |
| `set_filter({filter})` | B | 原校准场景及本人海图前置；原滤镜枚举 | 同上，B 见本人滤镜和光路 | 原参数错误／`NO_STATE_CHANGE`；同上 | +1 |
| `send_echo_request({replace_challenge_id})` | B | `IDLE/INVALIDATED` 须传 `null`；有活轮须引用当前 ID。当前光路可锁 | 将旧轮记为已替换（如有），创建新轮 `OPEN`；两端获当前 ID 及授权形状/字幕 | `EVIDENCE_STALE` 刷新引用；`PRECONDITION_NOT_MET` 恢复光路 | +1 |
| `return_echo_reply({challenge_id, beats})` | A | 活轮 `OPEN`，ID 与代次匹配；`beats` 严格两个允许的符号 | `RESPONDED`，记录服务器认可的回复；A 见提交通过，B 见当轮授权回读 | `EVIDENCE_STALE` 等新轮；`ECHO_REPLY_WRONG` 保持 `OPEN` 后改序；当前轮已回应返回 `ECHO_STAGE_MISMATCH` | +1 |
| `verify_echo_reply({challenge_id})` | B | 同轮 `RESPONDED`，检查回复来源、序列和光学代次 | `VERIFIED`；双方只见验证成功与 B 可锁状态 | `EVIDENCE_STALE` 或 `ECHO_STAGE_MISMATCH`；等有效回复，已验证则直接锁 | +1 |
| `lock_signal({challenge_id})` | B | `VERIFIED`，同轮同 `optics_rev`，原锁定前置全真 | 同次消费并永久写 `signal_locked`，双方进 `repair` | `EVIDENCE_STALE` 或 `ECHO_STAGE_MISMATCH`；恢复光路重做。已锁的新请求拒绝 | +1 |

**通关。** 光路就绪 → B 发短、长 → A 按个人记号回长、短 → B 验证该回复 → B 锁信号，两边看本人检修景。

**失败、并发和重连。** A 回短、长得 `ECHO_REPLY_WRONG`，同 ID 的挑战可改答。滤镜琥珀→蓝→琥珀产生两个新代次，连已验证的旧轮也失效。A 回信与 B 换轮、B 锁与 A 调角共享 CAS，先提交者决定当前状态；后一请求刷新后须符合当前挑战，已进 `repair` 后不能再改校准光路。A/B 任一端掉线可从 `OPEN/RESPONDED/VERIFIED` 原地恢复；镜像只投影获准的当轮形状、阶段和动作引用，不给 B A 的私有规则卡，不向 A 发 B 的完整波形历史。锁定只演出一次。

## 4. L05 · 潮汐证据交叉验证

**进入条件。** `repair`，且 L04 已达持久校准里程碑 `clock_calibrated`。A 首次修钟须满足原齿轮、供电与稳妥修法及当前 L04 校准。已经修好的机械事实跨停电保留。A 的档案证据描述不随供电而改变。B 的初扫、复扫和资格都依赖当前塔供电与修钟状态。

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| `WAIT_REPAIR` | 已进 L05，时钟未修好 | A 稳妥修钟 → `COLLECTING`；缺电先恢复 L04 的供电就绪 |
| `WAIT_POWER` | 钟已修好，当前塔失电 | 恢复供电 → `COLLECTING`；A 已读档案与提交仍可取用 |
| `COLLECTING` | 钟已修且有塔电，缺 A 的提交或 B 的当前初扫 | 两份都存在 → `READY_FOR_RESCAN`；断电 → `WAIT_POWER` |
| `READY_FOR_RESCAN` | A 的独立档案提交及 B 的当前初扫都存在，尚未签发验证 | B 定向复扫、产生唯一有效候选 → `VERIFIED`；失败不退出，B 可换扫描方案 |
| `VERIFIED` | 保存同一配置代次的初扫、定向复扫与有效验证 | B 确认 → `CONFIRMED`；重扫替换或条件变化使资格失效，回到相应等待/收集态 |
| `CONFIRMED` | 消费验证、写 `route_confirmed` 且进入 `decision` | 终态；L06 的两种引航安排仍由双方决定 |

服务器将范围表示为 `early/middle/late` 的有限集合，身份来自可信的观察与测量记录。A 的候选由服务器从版本化潮刻资料产生，示例资料支持 `{early,middle}`；客户端不能提交集合、窗段或证据文本。B 初扫模式表示实际扫描覆盖，下面的候选及复扫结果为可复现的设计样例；后续新内容须纳入同样的可达性检查。

| B 初扫模式 | 内容产生的本人候选 | 与 A 范围相交 | 复扫路径 |
| --- | --- | --- | --- |
| `quick`（粗读） | `{early,middle,late}`，分辨率不足以排除 | 两个候选 `{early,middle}` | `TIDE_OVERLAP_AMBIGUOUS`，按本人仪表提示改沿岸细扫 |
| `outer`（外缘） | `{late}`，仅有外缘样本 | 空 | `TIDE_NO_OVERLAP`，改扫与潮刻可共同覆盖的区域 |
| `coastal`（沿岸） | `{middle,late}`，早段逆浪已排除 | 唯一 `{middle}` | 服务器对该段执行连续航路的定向复扫，成功签发 |

签发条件为 `candidates(A.range_id) ∩ candidates(B.scan_id)` 的大小恰为 1，且在当前 `tide_config_rev` 下对该窗口有完整、连续航路的新测量。复扫由 `verify_tide_sweep` 触发，服务端在同一次提交生成不同于初扫的 `rescan_id` 及 `verification_id`。复扫记录引用 `parent_scan_id`、`range_id`、唯一窗口、角色 B 与当前代次，验证引用两个不同类型 ID 及 A 的提交。如果重试走去重路径则不会生成第二次测量。缺连续读数的单候选路径返回 `TIDE_RESCAN_FAILED`，保持原证据，允许换模式或调整供电重新收集。发布内容须保证经过可理解的补测步骤可得到至少一个完整的沿岸复扫；无出口的内容禁止发布。

## 6. S05 · 对位、机械锁与接近许可

**进入条件。** 在 `boarding` 已接轨，`signal_confirmed` 且灯号为 `blue_double_flash`，S04 的持久 `station_signal_crosschecked` 已确认。已有站台对照决定正确轨位为 `track_2`。A 可选择合法错误轨道以探索，服务器根据真实轨位及轮缘间隙决定是否能锁；发车需要 B 当前引擎和灯开、声呐关（4/5），保持原预算。

| --- | --- | --- |
| B 发车 vs A 改轨 | 发车和许可消费生效，改轨收到 409；刷新后已进决策场景，不能改轨 | 改轨作废观察、锁、许可；发车收到 409；即使调回并刷新，旧许可返回 `EVIDENCE_STALE` |
| B 发车 vs B 另一会话改能源 | 发车生效，配置命令 409；决策场景不再开放接车配电 | 能源变更作废许可、保留机械锁；发车 409；即使恢复原供电，需重新签发许可 |
| B 同 UUID 的两个发车 | 首先成功的写入消费和回执 | 另一请求重读回执后返回同一接受版本，不产生新发车事件 |
| B 不同 UUID 的两个发车 | 首先成功的写一次 | 败者 409；刷新后仍使用新 UUID 提交则 `PUZZLE_COMPLETE`，完档后遵循 `SAVE_COMPLETED` |

**通关。** A 对位二号轨、查间隙、机械锁合；B 配好引擎和灯，读当前锁并签发接近许可；B 发车，许可与到站状态一同落盘。能源准备可与 A 对位并行，许可必须等有效锁。

**失败与重连恢复。** 错轨先调回，未通电先配能，缺锁等待 A 检查。正轨→错轨→正轨使旧锁/许可失效；开灯→关灯→开灯也不能恢复旧许可。A 离线时如锁仍有效，B 可用当前授权状态继续；B 离线时 A 能完成锁但无权发车。返回时两端从个人快照派生状态，已发车仅呈现静态到站，不再执行或演出。双方暂停不设动作同秒的时限。

## 7. pytest 验收设计

使用两个版本化测试发布包、固定的观测数据和真实规则入口。新增用例将来按领域、投影、仓储/API 分层；仓储并发矩阵使用独立应用/连接、真实 SQLite 与真实 MongoDB。同步栅栏让两个提案读到同一版本，控制先提交哪方；禁止用两次顺序请求代替 CAS 竞争。重启组至少包含同一数据库重开、提交后响应丢失和真实 WebSocket 重新连接。此处仅登记用例与断言。

| 共用用例 | 测试安排 | 必须断言 |
| --- | --- | --- |
| C01 · 角色与命令输入 | 将四张操作表的每行参数化，分别以正确/错误角色调用；再测非成员，假角色、额外字段、错类型、跨存档 ID | 合法角色按原状态可执行；错角色拒绝。非成员看不到存档。猜测 ID 无权读取。错误的状态树、版本、回执集、历史、事件和播放均保持原值 |
| C02 · 同 UUID 和新 UUID | 对每个成功命令立即重送原信封，再于状态变化、配置失效或终态后重送；同 UUID 改参数、改原期望版本；两个角色和不同档复用同 UUID | 原 `accepted_version`、当前本人投影、`duplicate=true`，无重复对象或副作用；改指纹拒绝；不同授权域独立 |
| C03 · 不同请求并发 | 两个提案在同一版本通过规则预检，再以不同 UUID 竞争提交；交换先后 | 只有一个接受版本、一个回执和对应变化；败者得到 409 或旧版本拒绝，无自动重放；同 UUID 竞争走 C02，旧完成事实仍在 |
| C04 · 断线与隐私 | 四条主链每个写操作后重开仓储，分别用 A/B 读本人 HTTP 与 WS，先回归者交替；在 CAS 后丢弃响应并查原回执 | 未提交草稿不可成为证据。两端最新版本一致，各自私有标记只出现在授权快照；历史与当前字段分开。重连、HTTP 补偿、重复提交均不重复一次性演出 |
| C05 · 永久事实与旧版本兼容 | 完成各谜题，经过配置微调、重连、事件截断及重送，再用新 UUID 试重复动作；同库载入发布版 1.0.0 | 永久里程碑各一，恢复无新事件；旧档无新门槛、四结局仍可达、旧命令形状和投影保持兼容 |
| C06 · 无关版本变化 | 每章在签发前后插入合法的无关动作，另测设置相同值及失败配置 | 全局版本可前进，但相关代次及活动证据保持。客户端刷新后可在新版本提交同一个仍有效的引用 |

| 章／用例 | 正常与错误路径 | 往返、并发、恢复与隐私断言 |
| --- | --- | --- |
| L03-1 · 锁定主链 | B 发起、A 正确逆序、B 验证和锁定，轨迹经过 `OPEN → RESPONDED → VERIFIED → LOCKED`。传错误序列、过早验证、错角色或直接锁定 | 错序后同一挑战可新 UUID 改答；立刻重送各成功请求无重复轮、无第二次锁定 |
| L03-2 · 换轮与光路 | 分别在已打开、已回复、已验证后切滤镜或角度再切回，另测同值设置和 B 手动换轮 | 历史挑战 ID 永远无效，正确光路可新建；无关动作不能废有效轮。A 回信/B 换轮、A 调角/B 锁的两种 CAS 先后都可恢复 |
| L03-3 · 半轮恢复 | 在 `OPEN`、`RESPONDED`、`VERIFIED` 时分别重启；响应丢失时查 UUID | 显示当前轮与授权回读；A 私人逆序说明和 B 私有波形历史在对端 JSON/WS/公共回顾及 AI 输入中缺席 |
| L05-1 · 证据绑定 | A 真实档案观察和范围 → B 初扫 → 定向复扫 → 确认。另试裸「中段」、伪造范围/样本、相同初扫 ID 冒充复扫、错角色或跨档 | 只有两名合法创建者和三个可信记录才能验证；复扫 ID 不等于初扫，正确窗只产生一次证明，不改变结局选项 |
| L05-2 · 空、多解和断电 | 先外缘或粗扫，另用可控内容触发唯一但不连续的复扫；再换沿岸。先只建初扫、再建验证，各自做塔→岸→塔 | 错误不写入半个验证；已修钟和 A 范围保留，B 的旧 ID 失效，实际重采可恢复 |
| L05-3 · 消费和回档 | B 确认与另会话断电、B 换初扫或 A 换证据竞争，交换先后；不同阶段重启 | 配置先变时不能确认旧资格；确认先赢只有一次航路事件。B 得授权 ID、不能读 A 私有潮刻；A 不收 B 的扫描范围或原始读数 |
| S03-1 · 双测量主链 | A 先标与 B 先近测两种顺序；同批远测、唯一定位、发布及安装。另试远测过早、错误标钉、换路线后混批、重复样本和报二号 | 近/远类型、ID、批次、参照和生成角色严格检查，真实两样本才能发布；A 在 B 发布前不可装，B 不可装 |
| S03-2 · 批次恢复 | 分别模拟坏读数、零/多/错误单一交集；重开重采。同时测试关闸再开、任一能源位关闭再开启、撤标再重标、挡片往返 | 各配置从 A→B→A 后旧批仍无效；换批次可保留同代 A 标记但不保留近/远样本；回档只见当前批或获准摘要 |
| S03-3 · 并发与公布 | A 初标/B 近测、A 改标/B 远测或发布、A 改闸/B 发布分别竞争；发布后改变勘测配置，再回档安装 | 提交结果与 CAS 先后一致。已发布位置永久保留、无第三样本或第二次公布，A 原始标钉和 B 原始测量不互泄 |
| S05-1 · 完整接车与可恢复前置 | A 对位、查间隙、上锁，B 配能、发许可并发车；另试错轨、间隙不合格、无锁、无许可、超预算、没开灯、开声呐 | 相应前置码，失败不改世界。恢复条件后合法路径可完成。A 无法签发或发车，B 无法查间隙或上锁 |
| S05-2 · 往返和并发 | 验证轨位 2→1→2、能源开→关→开；参照第 6 节四项竞争矩阵，包含两设备同角色 | 旧锁或许可不复活，能源变化不解锁；同 UUID 重送原结果，新 UUID 不消费第二次；每种先后准确计数 |
| S05-3 · 崩溃窗口与投影 | 分别在间隙后、锁后、许可后、发车与回执原子提交后重启；A/B 交错回归 | 当前资格与里程碑一致，旧许可不可发车。A 看不到三路能源和 B 许可 ID，B 看不到 A 间隙原始读数，已到站只恢复静帧 |

## 8. 未决风险与建议

| 风险或待定事项 | 推荐方案与实施门槛 |
| --- | --- |
| 新状态类型、引擎上下文和原子聚合 | 现有 `GameState.facts` 为按剧本声明的标量元组。建议扩展一个仅新剧本启用的类型化状态段，读取时按版本校验，服务层只为 ID 派生提供可信 Save 范围。不要将证据塞为任意 JSON 事实或另开不同步存储。正式实现前验证旧存档解码、SQLite/Mongo 持久兼容和容量；是否需 schema 迁移尚待技术验证。 |
| L02/L04/S02/S04 还停留在纸面 | 先定义章级持久锚点和实时前置，尤其 L04 断电恢复如何重新取得校准，以及 S02 的挡片配置。用固定测试装配单独覆盖本四章，再跑真实全链路。不能因为前章资格暂停而让后章永久无法恢复。 |
| 内容和参数尚未定稿 | 本文两拍、潮汐模式、近/远取景采用确定性样例；最终稿需同时提供可复测的正常与错误路径、文字/形状等价线索。禁止发布只能靠耗尽尝试找答案或没有有效测量出口的配置。 |
| 已知答案与真实合作 | 玩家可以交流计划和正确值。契约要求对端真实授权操作和当前证据，不能证明两个人实际各自推导。用盲测观察这一点，用固定音画提示支持听觉、色觉及弱网参与。 |
| 代次触发、历史保留与命令容量 | 在动作评审中逐项冻结每个代次的更新来源，并覆盖往返与无关动作。暂定每类保留当前及最近历史摘要，验收测试将验证不会因重试正常预算触及 512 条上限。极端容量耗尽沿用现有读取和回执行为，若试玩路径吃紧，再独立审查容量策略。 |
| 错误语义、并发与播放回归 | 审核版本限定的新增错误映射、权限投影和 CAS 败者后的读回。上线前执行双真库并发、重启及真实双端恢复；只有有效回执或获准实时更新可驱动一次性演出。 |

建议先审阅第 2 节共用规则和第 6 节发车竞争，再按 L03、L05、S03 看从私人输入到公开结果的递进。可用纸面例子复演 S05：B 手持旧许可，A 把二号轨拨到一号再拨回；读最新快照时旧锁已失效，B 不能发车，直到 A 重新查间隙并上锁、B 重新核准。下一环节如获授权，可先实现最小版本化状态、ID 及投影，再逐章接入具体规则和上述验收用例。本阶段止于规则设计。
